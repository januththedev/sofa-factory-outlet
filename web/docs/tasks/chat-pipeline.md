Read `web/docs/BUILD-GUIDE.md` first. Spec source in `../Plan.md`: the whole "Chatbot" section (budget design, "What happens to each message" steps 1–10, "Keeping relevance high", "In the interface" limits) and the golden-set paragraph. This is the most intricate module; follow the plan closely.

## You own
`src/lib/chat/**` (replace the contract stub `api.ts`: same exports and types; add modules below), `src/app/api/chat/route.ts`, `src/app/api/chat/feedback/route.ts`, `src/app/api/cron/eval-chat/route.ts`, `tests/unit/chat-*.test.ts`, `tests/db/chat.test.ts`, `tests/fixtures/chat/**`.

## Consumes (contracts implemented by others; code against the types, catch failures)
`searchKnowledge` (`@/lib/kb/api`, kb-core), `searchProducts` (`@/lib/catalogue/search`, store-listing), `suggestFor` (`@/lib/colour/engine`, colour-engine), `getAvailability` (`@/lib/bookings/api`), `getPublishedCards` (`@/lib/catalogue/cached`, real), settings (`getSettings`, real), `notify` (`@/lib/notify/bell`, real), `whatsappLink` (`@/lib/settings/get`, real). ## Build (modules in `src/lib/chat/`)
- `normalise.ts` (pure): lowercase, trim, collapse spaces, fix a small typo list, strip emoji, expand synonyms from a dictionary (built-in English/Singlish defaults plus rows from `synonyms`): "couch" → sofa, "corner sofa" → l-shape, "lakhs/lakh" amounts ×100,000, Sinhala/Singlish keywords (e.g. "sofa set mila" → sofa set price). Also `normaliseQuestion` for FAQ/gap keys.
- `faq.ts`: instant answer when the best `faqs` row (question or `alternatives`) has trigram similarity ≥ 0.6 against the normalised message (`similarity()` from pg_trgm); bump `hitCount`; answered with **no model call** and no budget use. Hours/location/delivery questions go here.
- `intent.ts` (pure): rules-and-keywords classifier into exactly seven intents: `find_products | product_question | cart_pairing | store_info | booking | small_talk | off_topic`, using page context (product on screen → `product_question`; cart context + pairing words → `cart_pairing`).
- `extract.ts` (pure): category, colour family, material, shape, seats, budget ("under 1.5 lakhs" → ≤ 150,000 rupees, "below 80k", "around 2 lakh"), room size ("12x14 ft", "small flat"). Returns what it found.
- `retrieve.ts`: products → `searchProducts` with the extracted filters (top 4; fall back to cards filtered in memory when search fails); knowledge → `searchKnowledge(query, { tags by intent, limit: 3 })`; pairings → `suggestFor` for the cart. Returns ids and scores for logging.
- `confidence.ts` (pure): decides when nothing scores above the threshold (no FAQ hit, no products, no chunks above the minimum): skip the model and hand off honestly.
- `templates.ts` (pure): template answers filled by code for product finds ("Here are 3 green L-shape sofas" + cards), pairings, store info (address/WhatsApp from settings only), booking help, small talk, off-topic ("I can help with sofas, furniture and booking a visit"). Never state a price that is not stored; price format `Rs. 12,490`; never state hours, delivery times or warranty terms unless they come from an FAQ/knowledge chunk. Target: 80% of messages answered without the model.
- `prompt.ts` (pure): strict prompt from the plan: rules (answer only from FACTS, at most 80 words, never state a price that is not listed, prices in LKR), numbered FACTS (knowledge chunks), PRODUCTS (one compact line each, e.g. `[P1] Emerald L-Shape | velvet | green | 5 seats | price on request`), CART summary, the last 4 turns, 2–3 short example answers per intent. Settings: temperature 0.2, max 250 tokens.
- `openrouter.ts`: streaming `POST https://openrouter.ai/api/v1/chat/completions` (`stream: true`) with the model list from settings (`chat.models`) or `chatModels()` from `@/lib/env`, **fallback to the next model on error/empty**, 15-second timeout (`AbortController`), parses SSE deltas into an async iterator; returns nothing (a "not configured" signal) when `OPENROUTER_API_KEY` is unset so the pipeline stays template-only. Never log the key.
- `verify.ts` (pure): answer guard — remove any product name that is not in PRODUCTS and any price that does not match the database (replace with "price on request" wording or drop the sentence), strip links and phone numbers the model invented, cap length.
- `budget.ts`: daily model budget = `settings.chat.dailyModelBudget` (45) minus buffer (5): count today's (Asia/Colombo, midnight reset) `chat_messages` rows with `answeredBy = 'model'`; also the per-session cap (`perSessionModelAnswers`, 3 per `sessionId`); beyond either, template-only mode with a WhatsApp hand-off for open questions.
- `log.ts`: write the user and assistant messages with intent, extracted details, retrieved ids + scores, confidence, `answeredBy`, model, latency; low-confidence and thumbs-down messages upsert `knowledge_gaps` (by normalised question, increment `timesAsked`) and create a bell notification (`knowledge_gap`) once per new gap.
- `pipeline.ts` + `api.ts` (`runChat`): orchestrates steps 1–10, yielding `ChatEvent`s in order: `meta`, optional `cards`, `delta`s (templates are emitted as one or a few deltas), `chips` (e.g. "Show it in grey", "Add to cart", "Book a visit", "Talk to a person"), `handoff` when appropriate, `done`. Creates or reuses the conversation by `sessionId`; stores `context`. "Talk to a person" / handoff creates a `handoff` notification with a link to `/admin/chat/` and a WhatsApp link whose prefilled text summarises the chat (last few messages). Handles Sinhala/Singlish input gracefully (no model → honest hand-off). `chatRateLimited(visitorId)`: 20 messages per 10 minutes (count recent user messages).
- Routes: `POST /api/chat/` (Zod-validated body `ChatRequest`; reject oversized messages > 600 chars; `chatRateLimited` → 429 JSON; streams **NDJSON** (one `ChatEvent` JSON per line, `content-type: application/x-ndjson`), Node runtime, `force-dynamic`, `maxDuration` 30); `POST /api/chat/feedback/` (`{ messageId, rating: 1 | -1 }`, flags thumbs-down and creates the knowledge gap); `GET /api/cron/eval-chat/` (bearer `CRON_SECRET`) runs the golden set (below).
- **Also replace the two contract stubs** `src/lib/chat/eval.ts` (`runGoldenSet`, with the exact `GoldenResult` type already there) and `src/lib/chat/explain.ts` (`explainChat`, powers the admin playground: runs one message through the pipeline with a throwaway conversation that is **not** logged to the public conversation list, returns intent, extracted details, retrieved chunks and products with scores, the exact prompt (null when no model is needed) and the answer). The admin chat/knowledge pages are written against those names.
- **Golden-set eval** (`eval.ts`): reads `content/golden/golden.json` (an array of `{ id, question, expect: { intent?, products?: string[] (slugs or name fragments), facts?: string[] (substrings that must appear in the retrieved chunks/FAQ answer), handoff?: boolean } }`, written by another agent); for each question runs retrieval (no model) and checks: knowledge hit@3 contains the expected facts, expected products appear in the top 4, intent matches; returns `{ total, hitAt3, intentAccuracy, answeredWithoutModel, failures[] }`. The cron route returns that JSON.

## Tests
Unit: normalise (synonyms, lakhs, Singlish), intent for each of the seven intents, extract (budget phrases, colours, room sizes), confidence, templates (never state an unknown price or hours), prompt shape, verify (strips invented product names, wrong prices, links), budget arithmetic, SSE parsing and model fallback with a mocked `fetch`. DB (seeded data): instant FAQ answer uses no model; product question returns real cards; unknown question hands off honestly and records a knowledge gap; budget exhaustion forces template mode; the pipeline never throws when every dependency throws; NDJSON route handler with a mocked pipeline; rate limit. Put sample FAQs/chunks in `tests/fixtures/chat/`.

## Don't
Call OpenRouter in tests; invent business facts in templates; let the model see the whole catalogue; log secrets.
